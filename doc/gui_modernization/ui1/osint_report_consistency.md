# UI-1 OSINT and report consistency

## Previous behavior

OSINTFindingDialog edits provider, result/source URLs, title, similarity, first-seen estimate, source type and notes. Existing helpers also record reviewed/no-match and provider attempts. Previously each saved edit mutated the in-memory OSINT object and called `update_summary`, which reran build_summary_result. That existing engine intentionally accepts OSINT as contextual evidence and can therefore affect aggregate interpretation/scores/confidence. Saved final summaries/traces were not regenerated by those edit handlers, so the visible result could diverge from disk.

The engine's OSINT interpretation is not changed. Instead, UI-1 makes the synthesis boundary explicit: launch captures OSINT and scene context; completion calls the existing reasoning operation once with those launch-time values. **Post-analysis edits do not invoke reasoning.** To include new annotations/configuration in a new forensic result, explicitly run analysis again. This is an intentional current-GUI behavior change required to prevent silent confidence/score recalculation, not a change to OSINT thresholds or evidence rules.

## Transaction and revision flow

1. Dialogs receive detached draft annotations and capture the session ID before opening.
2. Cancel leaves the session/revision untouched. If selection changes while a modal event loop runs, an accepted draft still belongs to its original session and is rejected for the new session.
3. A committed draft is validated/serialized, written using the existing OSINT serializer into a staging directory and atomically replaces the session's osint_results.json. The additive investigation metadata records session ID and annotation revision; existing OSINT loader ignores the extra field.
4. Only a successful save advances the in-memory revision and replaces the displayed OSINT object. Failure retains the previous annotations and reports an error; it cannot silently accept an unsaved draft.
5. Commit invalidates the cached report/presentation, refreshes the immutable snapshot and narrative's explicitly separate current-annotation appendix, then regenerates a report for a completed active result. If analysis is still running, its launch-time annotation snapshot remains unchanged; completion records both launch and current revisions.

The forensic summary's sections—including its original OSINT section—remain the analysis-time record. Current annotations appear separately in JSON `annotations` and the labeled HTML/TXT appendix. `investigation.analysis_annotations`, analysis_annotation_revision, configuration, scene_context and profile describe what the authoritative synthesis actually used; annotation_revision describes the current appendix. Both displayed and exported narratives derive from the same frozen summary plus current annotations. Tests forbid any call to synthesis after post-analysis annotation edits.

## Report publication

`create_report_snapshot` requires COMPLETED and binds session_id/result_id/annotation_revision to immutable payload JSON. `persist_report_snapshot` checks that binding before writing and before publishing. Every generation is written beneath:

`<run>/report_revisions/<result_id>-a<annotation_revision>-<generation_uuid>/`

Inside it, existing filenames/layout remain: summary/final_summary.json, .txt, .html and reasoning trace JSON/TXT. Current annotations are also saved as osint_results.json. Only after all required writes succeed does an atomic replace publish `<run>/current_report.json`, pointing at the completed summary and recording its investigation metadata. Session.report_revision then marks the current report synchronized. A write failure leaves the prior pointer intact and accurately identified as its older revision; the GUI marks its report stale and exposes an explicit retry instead of revealing it as current. Partial unreferenced generation folders may remain for diagnosis.

Missing optional legacy trace fields can break the old narrative renderer. In that case the raw trace JSON remains exact and the text artifact explicitly contains recorded fields without reconstructed interpretation. Filesystem errors still fail report publication. No report failure changes forensic findings or replaces them with fabricated values.

The existing Open Results Folder action now publishes/retries the current revision and reveals its final summary JSON. Existing serializers continue supporting direct old SummaryResult calls; dictionary support is additive. RunRecorder artifact paths are updated to the published generation. There is no new report layout or export wizard beyond the necessary annotation/revision appendix.

## Compatibility and imports

Legacy `summary/final_summary.json` and new `current_report.json` can be opened through File → Open Stored Summary. Missing source paths are inferred only from an existing analysis_run.json manifest when available, otherwise remain unknown. Legacy OSINT beside the run can be loaded without changing it. New reports carry current annotations directly. Import is non-destructive and creates new local identities; original metadata is retained under historical_identity. Missing historical revision metadata stays absent.

Legacy stem-based annotations are imported on image selection only when their existing SHA-256 matches the selected file. Different files with the same stem cannot inherit each other's notes. New sessions and runs have isolated directories. Generated validation images/results remain Git-ignored.

## Limits

The report pointer is the publication boundary; the entire disk is not a transactional database. Disk-full/permission failures can leave unreferenced staging/generation directories. No automatic cleanup is performed. The synchronous current serializers may briefly occupy the GUI thread; moving large exports to a guarded worker is future work. Imported raw traces preserve their original content and limitations; import does not validate cryptographic provenance or reconstruct missing historical detector state. Post-run configuration changes apply only to the next analysis.
