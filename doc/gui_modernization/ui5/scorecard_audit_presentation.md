# Scorecard audit presentation

Suspicious and benign totals come from reasoning_trace.scorecard. The UI displays their stored floating-point representation without converting heuristic values into percentages. Contribution rows show raw base weight, credited contribution after numerical allocation, reliability multiplier, final adjusted **base** contribution, suppressed credit, classification and recorded reason. These are not additive per-hypothesis probabilities or complete post-aggregate contributions.

The second scorecard mode exposes component_operations in their recorded order, penalties, raw and final mechanism fields, reliability adjustments, domain-bonus coefficient, aggregate transforms, aggregate scores and the full numerical_deduplication audit. Details retain adjustment-stage and unresolved-relationship explanations. Historical base_evidence is shown when allocation rows are absent; missing adjustment fields remain Not recorded rather than being equated to zero.

`check_recorded_calculation` calls the existing pure `scorecard_integrity.reconstruct_scorecard_calculation` for complete valid version 2a calculations. It compares recorded totals and component fields to replayed values with the backend's 1e-12 absolute/relative tolerance. Outcomes distinguish Reconciled, Mismatch, Incomplete and unavailable/invalid ledgers. It never assigns replayed scores back to the session, the card, reports or hypotheses. Unsupported versions remain unavailable. This is arithmetic validation, not confidence reassessment or a competing scorer.

The existing documented replay sums credited base weights plus domain bonuses, replays add/multiply/maximum component operations, applies the recorded camera multiplier, caution penalty, zero floor, geometry and photo-context factors. The GUI consumes that implementation instead of duplicating its formula. Exact scalar values are copyable in the detail pane and full original trace. A score such as 6.675 is not a 66.75% probability.
